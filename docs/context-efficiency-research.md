# Context efficiency and prior art

Research checked 2026-10-29. Repository descriptions are maintainers' descriptions, not independently reproduced results. This is an analysis, not evidence that Threadmark saves tokens.

## What a local retrieval cache can and cannot save

Threadmark indexes selected historical user and final assistant messages in local SQLite FTS5. On a matching later prompt it can add short, project-scoped excerpts, excluding the active session. A useful excerpt *might* avoid rediscovery, repeated questions, or tool calls; the excerpt also adds input tokens and may trigger further verification. Its net effect is an end-to-end empirical question. It does not directly remove earlier context from the current session or control OpenAI's prompt cache.

OpenAI's [prompt caching documentation](https://developers.openai.com/api/docs/guides/prompt-caching) describes reuse of exact prompt prefixes, while its [Codex prompt caching discussion](https://developers.openai.com/cookbook/examples/prompt_caching_201) describes stable prefixes in the CLI. Changing a prefix can affect cache reuse, but the impact of Threadmark's hook output on actual Codex cache hits needs measurement, not assumption. API cached-input accounting and ChatGPT subscription usage limits are different observables; do not translate a token delta directly into a subscription saving. Separately, OpenAI's [compaction guide](https://developers.openai.com/api/docs/guides/compaction) describes reducing long-running conversation context while retaining useful state; this is not the same mechanism as cross-session retrieval.

[Codex hooks](https://learn.chatgpt.com/docs/hooks) deliver `UserPromptSubmit` additional context as developer context, and transcript format is not a stable hook interface. Treat remembered content as potentially adversarial and stale even when delimited. The documentation warns that hook context accumulates, and states an approximate 2,500-token default threshold before full output is saved to disk with a shorter preview. That threshold is not a retrieval budget or a hard privacy boundary. [Plugin hooks](https://developers.openai.com/plugins/build/plugins) require trust and scripts must exist in the execution environment.

## Comparison: related projects

| Project | Relevant mechanism | Implication for Threadmark |
| --- | --- | --- |
| [Codex Memory Kit](https://github.com/ghostarc249/codex-memory) | Maintainer describes SQLite/FTS5, deterministic offline hash-vector hybrid search, optional hooks and MCP, a semantic threshold, and bounded recall. | Compare wording-drift recall and irrelevant-hit rates on the same fixture before adopting hybrid retrieval. A hash vectorizer does not by itself establish semantic understanding. Its documented default project scope is the Git root directory name; Threadmark's canonical-path isolation avoids basename collisions, with a different worktree-sharing tradeoff. |
| [codex-lcm](https://github.com/Team-Volt/codex-lcm) | Maintainer describes a local SQLite/FTS index, structured lineage across sessions, turns, events, checkpoints and summaries, plus tools. | Provenance and progressive drill-down are useful ideas; indexing transcripts and summary DAGs increases complexity and privacy exposure, so retain explicit import and start with lightweight source identifiers. |
| [session-recall](https://github.com/AbsoluteMode/session-recall) | Maintainer describes cross-client history search via MCP and local semantic retrieval. | On-demand recall is an important control variant: it avoids injecting results on every prompt, but tool descriptions, calls and model decisions also cost tokens. Compare it experimentally; do not assume it is cheaper or equivalent to automatic recall. |
| [claude-mem-lite](https://github.com/sdsrss/claude-mem-lite) | Maintainer describes FTS5 plus TF-IDF hybrid retrieval and a reproducible synthetic retrieval benchmark including hard negatives. | Build an adversarial, labeled fixture with no-hit cases and measure the production retrieval path before adding search machinery. Its published numbers are not a Threadmark or Codex end-to-end comparison. |
| [ContextSniper](https://github.com/Calluking/ContextSniper) | A code-evidence selection system, rather than a cross-session conversation cache. Its [paper](https://arxiv.org/abs/2607.01916) reports pilot token and cost results in particular agent/repository-repair settings. | Test compact, recoverable evidence packets and end-to-end outcomes. The paper's reported reductions do not transfer to Threadmark; tasks, agents, corpus and baselines differ. |

## Recommended research and design sequence

1. **Establish a baseline first.** Make a synthetic, versioned fixture with labeled queries, relevant historical excerpts, plausible distractors, paraphrases, stale or conflicting facts, no-answer cases, project boundaries and active-session exclusions. Measure recall@k, precision@k, no-hit false-positive rate, output characters and latency. Split development from held-out cases; use the actual retrieval function and record corpus/configuration versions.
2. **Measure usefulness and total cost separately.** On permitted synthetic/public tasks, run paired fresh Codex sessions with Threadmark disabled versus enabled, same repository state, prompt, model/settings and tools. Include tasks with no useful history. Capture correctness or acceptance tests, independently scored evidence use and stale/malicious compliance, total input/output tokens, cached versus uncached input where available, tool calls, elapsed time and all hook overhead. Repeat and report distributions and failures. Include an on-demand or no-injection variant. Avoid reading a developer's private conversations; use isolated temporary homes. A local excerpt's character count is not an exact model token count. Any accounting inaccessible through a particular surface should be reported as unavailable.
3. **Improve selective retrieval before broadening storage.** Evaluate score and minimum-match thresholds, ambiguity/no-hit abstention, diversification, duplicate suppression, and excerpts centered on matched passages rather than the first characters of a message. Calibrate against held-out negatives, including short identifiers and paraphrases. Never weaken project/session boundaries to raise recall.
4. **Give users useful provenance and controls.** Surface timestamp, role and stable opaque source identifier, with explicit local inspection and deletion; investigate freshness signals and conflicting decisions. A later timestamp is not proof of correctness. Avoid persisting or logging raw prompts merely for telemetry.
5. **Keep optional expansion behind evidence.** A standard-library lexical baseline is inexpensive to operate; compare an opt-in on-demand interface or hybrid method only if measured failure cases justify extra tools, dependencies and security surface. More captured content, embeddings, automatic summaries and background watchers each create storage, latency, trust and maintenance costs.

The primary success criterion should be task success without harmful stale-context behavior, followed by measured token and latency deltas. A system that lowers tokens by omitting necessary evidence is not a successful optimization.

## Threadmark-specific decisions

Inspection of `context_cache/store.py` and `hooks/threadmark_hook.py` suggests the following order, subject to the measurements above:

1. **Build the evaluation harness first.** The existing tests verify boundaries and basic matching, but do not establish retrieval quality or net token savings. Separate a fast deterministic retrieval benchmark from paired Codex task runs; do not require network access for the former. Report results, fixtures and configuration, not a headline savings percentage from a single run.
2. **Fix evidence selection if the fixture confirms the failure.** The search takes up to 12 query terms, ranks up to 100 OR matches by FTS5 BM25, then requires two matching terms for multiword queries. It returns the beginning of each message, not the matching passage. One long first result can consume the entire 1,200-character excerpt budget, even when the useful match occurs later. Test passage-centered snippets, per-result caps, deduplication and calibrated abstention against the same held-out cases.
3. **Measure the entire injected payload.** The 1,200-character limit applies to excerpt text, not the JSON metadata, explanatory wrapper, or escaping; non-ASCII text can expand under JSON escaping. It is not a model-token limit. Account for repeated hook injection across turns and compare actual input and cached-input usage where the execution surface exposes them.
4. **Evaluate automatic versus on-demand recall.** Automatic retrieval has no model tool-selection step but may add irrelevant context repeatedly; on-demand search adds tool-schema and call overhead and may miss useful history. Compare both on the same tasks, including tasks with no useful history. Retain the existing path and session isolation in both.
5. **Add controls only where they solve observed problems.** Targeted deletion, a local dry-run explaining match selection, and opt-in durable notes are plausible follow-ups. Store minimal provenance and avoid persisting raw query telemetry by default. Do not introduce embeddings, summarization calls, a transcript watcher, or shared worktree scope until a measured failure justifies the extra dependency, privacy exposure and operational burden.

The recommended product direction is a small, private cross-session evidence tool with an honest benchmark, not a replacement for Codex's in-session compaction or provider-side prefix cache. These are design recommendations, not implemented behavior or verified performance improvements.
