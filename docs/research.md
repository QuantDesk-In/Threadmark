# Codex integration research

Checked 2026-10-29 against the current official documentation; verify against the target Codex release before relying on these interfaces.

## Supported integration

- [Codex hooks](https://learn.chatgpt.com/docs/hooks) accept a JSON object on stdin, including `session_id`, `transcript_path` (nullable), `cwd`, `hook_event_name`, and `model`. The transcript format is **not a stable hook interface** and can change. Do not depend on transcript parsing for basic capture.
- `UserPromptSubmit` receives `turn_id` and `prompt`. It can return `{ "hookSpecificOutput": { "hookEventName": "UserPromptSubmit", "additionalContext": "..." } }`; the text is added to the model as developer context. A hook must explicitly frame retrieved text as untrusted historical evidence, never instructions; because it is delivered at developer priority, delimiters alone are not a security guarantee. See [hook event details](https://learn.chatgpt.com/docs/hooks).
- `Stop` receives `turn_id`, `stop_hook_active`, and nullable `last_assistant_message`; on successful exit it expects JSON output. This allows paired prompt/final-response capture without reading unstable transcript files. An absent final message and interrupted turn require graceful handling. `SessionEnd` is not an immediate turn-end event; it fires on session closure or after an unopened idle session, and its default timeout is short. See [hook event details](https://learn.chatgpt.com/docs/hooks).
- `SessionStart` can inject `additionalContext` and fires on startup, resume, clear, compact, and fork; `SubagentStart` supports additional context. Query-specific retrieval at `UserPromptSubmit` is preferable to indiscriminately injecting global memory at session startup. Hooks execute only where installed scripts exist. [Plugin packaging](https://developers.openai.com/plugins/build/plugins) supports plugin hook configuration, `PLUGIN_ROOT` and writable `PLUGIN_DATA`.
- Hooks require user trust before they run; enabling or installing a plugin does not grant trust. Codex documentation describes plugin hooks as non-managed hooks. This is a real setup requirement, not something a plugin can silently bypass. See [plugin packaging](https://developers.openai.com/plugins/build/plugins).
- Default `additionalContext` handling has an approximate 2,500-token threshold, after which the full content is saved to disk and only a preview is sent. Set `additionalContextLimit` if appropriate, and independently enforce a much smaller retrieval budget. See [hook output limits](https://learn.chatgpt.com/docs/hooks).
- Hooks are scoped to enabled configurations and execution environments, not a guarantee across remote machines or every client. The [plugin architecture](https://developers.openai.com/plugins/concepts/plugins) notes that hook scripts must be available on the execution host. `codex-cli 0.165.0` was present in the local environment at research time; availability and feature support should be tested rather than inferred from version.

## Product implications

Automatic storage and retrieval can use `UserPromptSubmit` and `Stop`, backed by a local database. This is a *retrieval cache*, not OpenAI's server-side prompt cache: injected text itself consumes context, and reduced token use or higher accuracy requires measured end-to-end evidence. Record provenance and time, restrict retrieval to relevant project scope by default, avoid credentials and sensitive content, provide inspect/delete/disable controls, and guard against replaying malicious or stale instructions. No heuristic secret filter or prompt-injection wrapper guarantees safety. Raw final answers can be verbose, wrong, or contain sensitive data, so conservative extraction and configurable opt-out are important.
